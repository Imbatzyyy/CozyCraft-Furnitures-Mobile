# CozyCraft 1.0.89 — secure optional web updates

## What ships

Both the original and no-side-menu apps retain their existing navigation, team content, silent tabs, checkout limits and display name **Cozy Craft Furnitures**. The original uses Android build 91 / iOS build 78; no-menu uses Android build 92 / iOS build 79. Both use bundle/application ID `com.cozycraft.furniture`, so they replace one another on a device rather than install side by side.

This is the **one-time native enabling build**. Previously installed 1.0.88 and older binaries do not contain the updater and must first be upgraded with the new APK or an Xcode/native distribution build. Afterward, eligible HTML/CSS/JavaScript/assets patches can be offered inside the app. Native plugins, permissions, signing entitlements, native SDK changes and incompatible dependency changes still require a new native build. Do not promise all future changes can bypass installation.

## Customer behavior

- A signed, version-compatible update appears only on a safe, idle shopping screen.
- **Update now** downloads/verifies the patch and briefly reloads the app; **Later** postpones that release for 24 hours.
- Account → **App updates** also permits a manual check, including guest accounts.
- Signup, onboarding, checkout, payment callbacks, editors, open dialogs, active requests and background state block activation.
- Automatic checks are at most once per four hours while foregrounded; failures back off for 15 minutes. There is no database realtime subscription or background polling job.
- The small manifest is cacheable. The full package (approximately 24 MB compressed in this release) is downloaded only after consent. This uses Storage egress, not zero egress. Wi-Fi is recommended.
- A newly selected bundle must render the app and acknowledge startup. The native watchdog rolls back if it does not become ready within 60 seconds. This is startup recovery, **not** a guarantee against every late-running logic bug.
- Orders and customer records remain in the existing backend. Do not reset application storage or change storage origins in a patch.

## Security boundary

Two independent RSA-2048 signing keys separate original and no-menu channels. The shell verifies RSA/SHA-256 signed metadata before trusting notes or URLs. It enforces the exact project/bucket/channel path, installed native version and platform build, monotonic release sequence, expiry, and a 64 MB package cap. The native plugin independently checks the authenticated SHA-256 package checksum. Tampered or mismatched packages fail closed.

The encryption format is the updater's supported authenticated-checksum protocol, not a promise of code secrecy. All downloaded client code should be considered public. Never place service-role credentials, customer data or private keys in a bundle.

The `mobile-updates` Storage bucket is public-read and service-publisher-write only. Restrictive INSERT/UPDATE/DELETE policies deny both anonymous and authenticated app clients, including normal staff sessions. No customer-account privilege is added. Capgo cloud update endpoints, analytics endpoints and preview/channel switching are disabled.

Private signing keys are outside the repositories, in the release Mac's `~/.config/cozycraft-updates/`, mode 600. **Back them up securely and restrict access.** Do not email or commit them. Losing a key requires a newly signed native enabling build; compromising a key requires revocation/replacement and an incident response. Local replay protection cannot defend a rooted device or attacker with signing authority.

## Developer release procedure

Run from the intended mobile repository with Node 24 LTS and authenticated Supabase CLI access. Never mix frontend folders.

1. Make the eligible web change. Run `npm run verify:release` and `npm run test:browser`. Test the actual patch on Android and iOS; the preparation command alone is not device proof.
2. Pick a **new, strictly increasing sequence** for this channel/native version. Never overwrite or reuse an already prepared sequence.
3. `npm run update:prepare -- --sequence N --notes "Concise customer-facing fixes."`
4. `npm run update:stage -- --sequence N` uploads and verifies immutable artifacts, but does **not** change what customers are offered.
5. Validate the staged package on controlled test devices. Verify later/manual check, activation, checkout safety, cold start and rollback. The local QA scripts require a controlled emulator/WebView connection and are not customer features.
6. `npm run update:publish -- --sequence N --reviewed`
7. Verify the resulting signed channel pointer and test Account → App updates from the baseline native build. Record the artifact hashes, commit and evidence.

A per-channel local release lock prevents simultaneous release commands on this Mac. The publisher also rechecks the live sequence immediately before publishing the pointer. Supabase Storage has no compare-and-swap pointer transaction: **use one coordinated release operator**, not competing release hosts.

Native fingerprint checks refuse web publication if native source/configuration/plugins changed. `updates/native-baseline.json` is a reviewed native compatibility boundary; do not regenerate it just to bypass a failed preflight. Prepare a new native version/build instead.

Production dependency auditing fails closed on advisories or unavailable audit service. A successful audit receipt may be reused for at most 24 hours only for exactly the same lockfile; the command reports that timestamp.

## Withdrawal and recovery

`npm run update:pause -- --sequence NEXT_SEQUENCE` publishes a signed pause. It stops future offers/activations after clients retrieve it; it does not remotely erase an already running patch. Offline devices keep their installed app. If a running patch has a late-discovered defect, prepare known-good web source under a **higher sequence**, test it, and publish it. Never lower the sequence.

Local failed-start markers and native failed-bundle status suppress re-offering a patch that failed to boot. Network errors and an interrupted download leave the active app intact.

## Distribution limits

The APKs produced here use this project's existing debug signing identity for compatibility with its previous directly distributed test APKs. They are demo/test artifacts, not a Play Store production-signing setup. Do not uninstall first if preserving local data is important. iOS delivery still requires a valid Apple signing/distribution route; no App Store/TestFlight upload or physical-phone installation is implied by an Xcode build.

App Store-distributed updates must comply with Apple's review rules, especially 2.5.2. Keep OTA use to eligible maintenance/assets and do not use it to bypass review or introduce prohibited functionality.

## Release verification — 23 October 2026

The published channel pointers offer **1.0.89-r4** (sequence 4) separately for original and no-menu. Both signatures and native compatibility identities were verified after publication.

- Preparation checks passed: original storefront 485 tests; no-menu storefront 506 tests; Angular shell 37 tests per variant; cryptographic/adversarial updater 22 tests per variant; Xcode toolchain 11 tests per variant; type checking and lint.
- Browser regression checks covered onboarding, payment limits/returns, low-egress behavior, chat, navigation, reduced motion, text scaling and responsive layouts in Chromium/WebKit.
- Native Android applied the signed r4 package successfully in both variants. Tampered checksum and other-variant signing key tests were rejected. A deliberately non-ready test bundle triggered the native 60-second watchdog and recovered to the previously working bundle.
- Xcode 27.1 simulator builds and signed generic iOS device builds passed for both variants. All 160 web files matched the Android APK, native asset folders and simulator build.
- Actual iOS 27 simulator UI activation also passed for both live r4 channels, not just compilation: original bundle `HYxULktRxc` and no-menu bundle `tRhKWHdzQM` both reached native `success` status after rendering/acknowledgement. Original manual checking and no-menu automatic safe-screen prompting were exercised.
- Production-dependency audits reported zero advisories for both shells/storefronts. Final rechecks reused successful exact-lockfile receipts less than 24 hours old.
- Storage policy checks denied anonymous/authenticated client writes. The backend owns migration `20261022020000_mobile_signed_updates.sql`; this mobile repository does not deploy shared database migrations.
